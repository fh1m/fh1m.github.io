February 2024, a university robotics contest. The team bailed, the last servo burnt out and the components cupboard was empty. What was left: a 4WD acrylic chassis, an Arduino Uno with an L293D motor shield, an HC-SR04 ultrasonic sensor on a stalk, and one night. The robot was named after **Bhapa**, the campus cat, who has better obstacle avoidance and a better attitude.

The 2024 README promised intelligent object following, dynamic obstacle avoidance, enhanced exploration, and proportional *and* adaptive speed control. It was written at hour five. Two years later I read the code properly, found out what the robot had actually been doing, and fixed it.

## What v1 really did

| the 2024 README said | the code actually did | why |
|---|---|---|
| turns, backs up | **never turned, never reversed** | `adjustMotorSpeed(left, right)` sent `left` to motors 1 *and* 2 (front-left and front-right) and `right` to the rear pair. Each side averages front and rear, so both sides always match. |
| "move backward" | moved forward, slowly | AFMotor's `setSpeed()` takes a `uint8_t`. −255 becomes **1**, −200 becomes **56**. And every `run()` said `FORWARD` anyway. |
| follows objects at a safe distance | **drove into them, politely** | Within 25 cm, closer meant slower, but never stop. |
| dynamic obstacle avoidance | in a 5 cm band | Avoidance only ran between 25 and 30 cm. Anything nearer got "followed". |
| five exploration behaviours | five, half the time | `random(0, 10)`, with cases 0–4 only. |
| — | froze for up to a second | `pulseIn()` without a timeout waits a full second for an echo that isn't coming. |

So the 2024 robot was, in effect, a very determined forward-only cart. Every behaviour in the README existed in the source and nowhere else.

## v2: same robot, same single sensor

The new firmware compiles for an Uno at 5,030 bytes.

1. **Wiring:** left is motors 1 + 3, right is 2 + 4.
2. **Signs:** `setSpeed(|pwm|)`, and `run(FORWARD | BACKWARD)` from the sign.
3. **Sonar:** a 25 ms timeout, about 4 m. No echo means *nothing there*, not *freeze*.
4. **Following holds a distance instead of closing it.** Proportional on the error to 30 cm, with a ±4 cm dead band.
5. **Walls are boring.** One forward ray can't tell a cat from a wall, but *time* can: a wall's distance never changes. If the reading stays within 3 cm for 2.5 s, it's furniture. Turn away, find something that moves.

## Three robots, one room, one cat

A simulator runs the sketches line for line in a 3 × 3 m room: same thresholds, same random draws, same `delay()`s, with v1's hardware quirks switched on. A simulated Bhapa wanders at 0.15 m/s and stops whenever she feels like it, which is accurate.

Rewiring alone doesn't save v1. It turns now, but the follow rule still drives it into the first wall it meets.

<Pull>Wiring was the bug. The rule was the design mistake.</Pull>

## Lessons, paid for in one night

- **Read the library's types.** A `uint8_t` parameter turns a negative speed into a polite crawl, and the compiler doesn't argue.
- **Label your wires the way your code names them.** "Left" in a comment is not left in copper.
- **A sensor reading is a number. Behaviour needs a rule about *change*.** One ultrasonic ray will never tell a cat from a wall. A few seconds of memory will.
- **Never block on a sensor without a timeout.** The world is allowed not to answer.

Both firmware versions run live at [bench zero](/#bench-zero). Press v1 and watch it find a wall and commit to it.
