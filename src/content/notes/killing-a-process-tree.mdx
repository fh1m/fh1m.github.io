Killing `ros2 launch` orphaned every node it had started. Those orphans kept holding the Hailo-8 accelerator, and that surfaced an hour later, often in a completely different tool, as `HAILO_OUT_OF_PHYSICAL_DEVICES`, with no obvious connection back to the stop that had supposedly already happened.

## Two fixes, both measured, both wrong

**Attempt one** reset the inherited ignore-SIGINT state and signalled the launcher directly. The launcher didn't exit within 20 seconds, so the escalation sent SIGTERM, which `ros2 launch` doesn't forward to its children. They orphaned anyway.

**Attempt two** tried `setsid` and a process-group signal. `os.setsid()` failed in that execution context, the wrapper died immediately, and the stored PID pointed at a process that had never existed. The stop function returned success, having signalled nothing. It printed neither *stopped* nor a failure. It lied by omission.

Both attempts shared one broken assumption: that some other process in the chain would forward the signal. The fix drops it. `kill_tree` walks every descendant and signals each one directly (INT, then TERM, then KILL), because `ros2 launch` starts every node as its own child. The live process tree *is* the node list. Nothing needs to relay anything.

<Pull>Verified on hardware and correct are not the same claim.</Pull>

## The fourth bug only a test could find

A real test, written to spawn children that *ignore SIGINT on purpose*, found a defect the hardware couldn't have shown. `kill_tree` re-walked the process list at every escalation step. That looks equivalent to walking once. It isn't.

On real hardware this stayed invisible, because ROS 2 nodes happen to die on the first SIGINT. The defect had zero opportunities to matter, until a test deliberately created exactly the condition the tool exists for. The fix snapshots the whole tree *before* anything is asked to die.

<Fig src="/media/lab/meghdut-tui-2.webp" alt="A terminal UI showing live link bytes" caption="The other end of the same habit: if a tool can fail, make its failure visible. A stop that prints nothing is a stop you can't trust." wide contain />

Three hardware runs said it worked. One adversarial test said it didn't. The hardware wasn't wrong; it just never asked the question.
