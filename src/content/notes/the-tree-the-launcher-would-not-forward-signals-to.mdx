Killing `ros2 launch` orphaned every node it had started. Those orphans kept holding the Hailo-8, which surfaced an hour later, often in a completely different tool, with no obvious link back to the stop that had supposedly already happened.

## Two fixes, both measured, both wrong

The first attempt reset the inherited SIGINT-ignore state and signalled the launcher directly. It didn't exit within 20 seconds, so the escalation sent SIGTERM, which `ros2 launch` doesn't forward to its children. They orphaned anyway.

The second tried `setsid` plus a process-group signal. `os.setsid()` failed in that execution context, the wrapper died immediately, and the stored PID pointed at a process that had never existed. The stop function returned success, having signalled nothing. It printed neither "stopped" nor a failure. It lied by omission.

Both shared one broken assumption: that some process in the chain would pass the signal on. The fix drops that assumption. `kill_tree` walks every descendant and signals each one directly (INT, then TERM, then KILL), because `ros2 launch` starts each node as its own child, so the live process tree *is* the accurate node list and nobody needs to relay anything.

<Pull>Verified on hardware and correct are not the same claim.</Pull>

## The fourth defect

A real test found something the hardware couldn't. `kill_tree` re-walked the process list at every escalation step, which looks equivalent to walking once. It isn't.

Any child that ignored SIGINT simply outlived its parent and was never signalled a second time. On real hardware this stayed invisible, because ROS 2 nodes happen to die on the first SIGINT, so the defect had zero opportunities to matter. Until a test deliberately spawned children that ignore SIGINT, which is exactly the condition the tool exists for. The fix snapshots the whole tree *before* anything is asked to die.

Hardware runs test the cases the hardware happens to produce. Tests can produce the case you're afraid of.
