The plan named a canary: one test column, `torpedo_1`, which INT8 must not push below 15 inliers. It sounded sensible. It was also wrong, and following it would have killed a working feature.

The test itself was set up honestly. Re-run the murky-water clip table with the chip as the backbone and *everything else identical*: same post-processing, same MAGSAC, same 15-inlier trust bar, same protocol. The only variable was float32 on the CPU against INT8 on the Hailo. Every clip scored exactly what it scored before: 4/4, 3/4, 4/4, 4/4, 4/4.

## Read the tell

Nineteen of twenty columns cleared 15 inliers on CPU. The same nineteen cleared it on the chip. And the canary, `torpedo_1`, read 12 on INT8, which looked like a quantisation failure until you read the CPU column next to it.

<Pull>Reporting the wrong quantity is what lets a defect survive three attempts.</Pull>

Calling its 12 an INT8 failure would have condemned a working path on a case that was already below the line. The real question was never *did INT8 cost inliers* (it always does, a little) but *did it push any passing column under the bar*. None did.

<Fig src="/media/mongla-docs/robosub-torpedo.webp" alt="The torpedo board underwater with the detector boxing it and its openings" caption="The torpedo board in real RoboSub footage: the kind of clip the columns are made of." />

Measure the effect you actually care about, through the code path that ships, or you're measuring the harness. The scatter that made five columns *improve* on INT8 is the same scatter that would have made a dead canary look like a casualty.
