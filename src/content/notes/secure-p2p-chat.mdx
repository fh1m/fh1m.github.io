Two terminals, one TCP socket, no server in the middle. The chat starts in **plaintext on purpose**, so you can watch what an eavesdropper sees. Then `/share` runs a handshake (RSA-2048 with OAEP to move a session key, RSA-PSS signatures to prove who sent it) and every message after that is AES-256-GCM.

## Four questions

Secure chat answers four questions, and each one needs a different tool:

| question | the threat | the tool |
|---|---|---|
| confidentiality: can outsiders read it? | eavesdropping | AES-256-GCM |
| integrity: was it changed? | tampering | GCM's authentication tag |
| authenticity: is it really them? | impersonation | RSA-PSS signatures, key fingerprints |
| freshness: is it new? | replay | nonces, timestamps, sequence counters |

Confidentiality is the one everybody remembers. The other three are where real protocols break.

## The downgrade I added later

Going back to it, one gap stood out. A chat that starts in plaintext has to accept plaintext. So what happens if plaintext arrives *after* a secure session exists? A peer that holds the key has no reason to send it. Either something broke, or someone else is talking.

Now two things guard that line. Plaintext after a secure session raises a downgrade warning instead of being shown like any other message. And `/strict` refuses plaintext entirely, for when you'd rather drop a message than read a forged one. Four tests pin both behaviours.

<Pull>A protocol that quietly accepts the weaker option has a weaker option, not a stronger one.</Pull>

Rekeying (`/rekey`) rotates to a fresh session key through the same handshake. The protocol messages are newline-delimited JSON, deliberately readable, because the point of the project is that you can inspect every byte and see which property each one buys.
